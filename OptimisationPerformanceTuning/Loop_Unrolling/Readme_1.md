# Loop Unrolling в GCC

В прошлых постах я часто писал, что компилятор сам умеет вполне неплохо разворачивать циклы.

Но это всё же оптимизация, и важно понимать, когда она включается.

Можно использовать pragma-директивы, но это уже явные подсказки компилятору в коде.

А как заставить компилятор разворачивать циклы, не меняя исходный код?

Будем рассматривать примеры на GCC.


## Без оптимизаций (`-O0`)

По умолчанию компилятор практически дословно транслирует код в машинные инструкции.

```cpp
int sum(std::span<int> ints) {
    int sum = 0;

    for (auto value : ints)
        sum += value;

    return sum;
}
````

При компиляции с `-O0` в ассемблере будут присутствовать:

* вызовы итераторов;
* проверки границ;
* прочая служебная логика цикла.

То есть код будет максимально близок к исходному.

---

## Оптимизация `-O2`

На уровне `-O2` GCC начинает выполнять некоторые оптимизации циклов.

Для примера выше компилятор значительно упростит цикл, но разворачивать его не станет.

Однако ситуация меняется, если размер диапазона известен во время компиляции и кратен 2 или 4:

```cpp
int sum(std::span<int, 20> ints) {
    int sum = 0;

    for (auto value : ints)
        sum += value;

    return sum;
}
```

В этом случае GCC:

1. Разворачивает цикл с фактором 4.
2. Выполняет векторизацию через SSE.
3. Использует `xmm`-регистры для суммирования нескольких элементов одновременно.

Получается примерно такой код:

```asm
sum(std::span<int, 20ul>):
        lea     rax, [rdi+80]
        pxor    xmm0, xmm0
.L2:
        movdqu  xmm2, XMMWORD PTR [rdi]
        add     rdi, 16
        paddd   xmm0, xmm2
        cmp     rax, rdi
        jne     .L2
        movdqa  xmm1, xmm0
        psrldq  xmm1, 8
        paddd   xmm0, xmm1
        movdqa  xmm1, xmm0
        psrldq  xmm1, 4
        paddd   xmm0, xmm1
        movd    eax, xmm0
        ret
```

### Интересный момент

Если заменить размер `20` на `19`:

```cpp
std::span<int, 19>
```

то векторизация уже не сможет быть выполнена столь эффективно и оптимизация сломается.

### Вывод для `-O2`

На практике GCC способен разворачивать циклы с:

* фиксированным числом итераций;
* числом итераций, кратным 2 или 4;
* хорошими условиями для векторизации.

---

## Оптимизация `-O3`

На уровне `-O3` компилятор действует гораздо агрессивнее.

Теперь могут разворачиваться циклы даже с неизвестным заранее числом итераций.

Обычно GCC:

* добавляет обработку "хвоста" (tail processing);
* выполняет векторизацию при возможности;
* полностью разворачивает цикл, если число итераций известно во время компиляции.

Решение принимается на основе набора эвристик:

* размера цикла;
* предполагаемого выигрыша;
* увеличения размера бинарника;
* возможностей векторизации.

---

## Специальные флаги для разворачивания циклов

### `-funroll-loops`

Разворачивает все циклы, для которых количество итераций может быть определено на этапе компиляции.

Небольшие циклы могут быть развернуты полностью, так что от самого цикла ничего не останется.

Из документации GCC:

> This option makes code larger, and may or may not make it run faster.

Иными словами:

* код становится больше;
* производительность может вырасти;
* а может и не вырасти.

---

### `-funroll-all-loops`

Максимально агрессивный вариант.

Компилятор пытается разворачивать всё, что вообще можно развернуть.

Из документации GCC:

> This usually makes programs run more slowly.

То есть чрезмерное разворачивание нередко приводит к обратному эффекту:

* увеличению размера кода;
* ухудшению локальности инструкций;
* падению производительности.

---

## Итог

Не стоит слепо включать все возможные оптимизации только потому, что они *теоретически* ускоряют программу.

Всегда:

1. Измеряйте производительность.
2. Профилируйте код.
3. Проверяйте результат на реальных данных.

Во многих случаях достаточно просто довериться компилятору и использовать стандартные уровни оптимизации (`-O2` или `-O3`).

> **Don't follow the rules blindly. Stay cool.**
